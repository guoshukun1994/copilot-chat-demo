# 流式渲染压测基线

## 压测方法

1. 启动 `npm run dev:server`（mock SSE 服务，3001 端口）和 `npm run dev`（5173 端口）
2. 浏览器打开 `http://localhost:5173/?stress=1`，打开 Copilot 面板后会自动发送「压测」消息
3. mock 服务逐 token 推送长 Markdown，速率由 URL `?tps=` 控制：
   默认 40 token/s（便于阅读输出内容），压极限性能用 `?tps=500`
4. 右下角探针面板实时显示计数，流结束后数值即最终结果

注意：本文所有历史数据均在 500 token/s 下测得；用低 tps 跑压测时，
写入/渲染的"每秒速率"会随推流变慢而等比例下降，总量口径不变，对比时注意区分。

## 基线数据（改动前，逐 SSE 帧 setState）

| 指标 | 数值 | 说明 |
| --- | --- | --- |
| SSE 帧数 | 768 帧 / 1.85s | 约 415 帧/秒 |
| store 写入 | 770 次（437/s） | 每解析一帧就 set 一次 |
| 列表渲染 | 1530 次 | 约等于 770 x 2（StrictMode 双渲染），每次写入都触发整列表重渲染 |
| 气泡渲染 | 3056 次 | 每次列表渲染带动 2 个气泡（用户+助手）重渲染 |
| 放大倍数 | 2.0x | 气泡渲染 / 列表渲染 |

## 目标（rAF 合帧后）

浏览器 60fps 预算下，1.85s 的流理论渲染上限约 111 帧。合帧后「列表渲染」应从
1530 次降到百级，「气泡渲染」同步收敛；store 写入次数可以不变（合帧做在渲染侧）
或同步下降（合帧做在写入侧），取决于方案选择。

注意：React StrictMode 下渲染次数翻倍，改动前后对比看趋势即可，不要跨模式对比。

## 重负载对比（150 条历史消息 + 12 轮流式，约 20s）

切换方式：探针面板顶部按钮（逐 token / 合帧），或 URL 加 `?write=frame`。
面板切换会写入 localStorage，刷新重跑压测模式不丢。

| 指标 | 逐 token（基线） | 合帧（rAF） | 变化 |
| --- | --- | --- | --- |
| store 写入 | 8824 次（440/s） | 1760 次（88/s） | -80%，且 1 帧恰好 1 写 |
| 列表渲染 | 3704 次 | 3522 次 | ≈ 持平 |
| 气泡渲染 | 563000 次（152x） | 535336 次（152x） | ≈ 持平 |
| 实测 FPS | 16（最差帧 141ms） | 88（最差帧 47ms） | 5.5 倍 |
| 长任务（>50ms） | 1 个（145ms） | 2 个（99ms） | 最长 -32% |

结论：

- 合帧的价值不在「减少渲染次数」，而在「把渲染对齐到屏幕刷新节奏」：
  基线里大量提交挤在帧中间，错过垂直同步，渲染了也上不了屏；
  合帧后每次渲染都落在真实帧上（1760 次写入 ≈ 1760 帧上屏）。
- 少做的 7000 次写入 = 少复制 7000 次消息数组 + 少通知 7000 次订阅者，
  这部分是实打实省下的主线程时间。
- 气泡渲染 152 倍放大没有变——那是另一个变量（MessageBubble 未 memo），
  本次刻意不动，留作下一步优化的对照。
